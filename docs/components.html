    Official components and contribution decisions¶

    The 2026-11-18 UI/shell evaluation recommends reusing the appropriate official page/runtime foundation and adapting its presentation. Custom palettes, menus and layouts do not require a replacement app-shell SDK. Preserve ownership, input and backend authority; evaluate behavioral changes separately from appearance.

    The 2026-11-18 keyboard/input evaluation checks current official sources and supplements the historical comparison below. Use the official shared input backend when that runtime fits; adapt the Template's navigation subset for text-entry needs. A general replacement keyboard library is deferred. Existing prepared contribution pins remain unchanged.

    Reviewed 2026-11-16. Start with the official implementation that fits your project. This is a source-level comparison, not a security certification or a promise that two different build systems/components can be exchanged unchanged.

    Reuse, adapt or contribute¶

    Area What exists Mesh-specific difference Decision
    App shell and widgets Template BaseScreen, reactive bindings, status/nav widgets, Help and toast Mesh's title bar/viewmodel know about radio, nodes and unread chats Reuse the official shell; expose app-specific status fields rather than extracting the Mesh screen tree wholesale
    Keyboard Shared cp0 backend has the official symbol map/input contracts; Template's device map_evdev_key() only handles a navigation subset Mesh adds a portable per-device decoder and raw-event-to-editor regressions Prepare a focused Template integration using the official assignments, preserving navigation, simulator routing and tests
    Settings/storage Template theme/config and shared configuration service Mesh's atomic INI saves and chat-history policies contain domain fields Teach durable/private saves and opt-out semantics; adopt existing storage where suitable; no general persistence library yet
    Background work Shared runtime/process/callback services Mesh owns a radio daemon, private socket, guardian and transient lifecycle Pick the simplest architecture; reuse compatible official services and document any missing ownership/security behavior
    Camera/QR Official Camera and shared camera service Mesh needs cancellable capture, secret preview and confirmed channel import Keep a conditional recipe; inspect backend/image compatibility and qualify actual capture before extracting a camera abstraction
    Packaging/release Template CMake/CPack and AppBuilder/czdev Mesh has matching Debian arm64 CI and exact installed-runtime checks Preserve the official package contract; offer a reusable verification recipe without creating another installer
    Store checking Official policy and publishing tools This guide's offline preflight deliberately cannot publish Keep the small separate inspection tool and its pinned policy tests; it is not an alternative Store authority

    Concrete keyboard gap¶

    At the reviewed Template revision, the native map returns only selected navigation/shortcut keys. The shared launcher already has all 32 symbol assignments. The opportunity is reliable integration into this Template, not inventing a new keyboard layout or alleging the official shared map is wrong.

    An existing Template contribution also requests additional keys. Inspect its current state before proposing another upstream change. My prepared proposal records its exact base, scope, code provenance, tests and remaining qualification. It has not been submitted or accepted upstream.

    Evidence and limits¶

    The shared repository contains targeted tests for keyboard/input lifetime, screen cleanup, configuration failure/rollback, process handling and other services. See its runner and implementation snapshot. Selected source/tests and its build workflow were inspected; the complete upstream suite and device/image matrix were not rerun for this comparison. Do not equate the existence of tests, a green build, official ownership or a large test count with blanket reliability. The Template's navigation demo and the broader shared SDK are different integration paths.

    CMake/SDL and SCons/Kconfig do not automatically share build flags, input event formats, ownership or callback conventions. Review dependencies and licenses, match the actual image, and exercise the complete path used by the app. The BSP cross-build archive is a target sysroot; it is not by itself a ready-made app UI kit.

    When a separate library is justified¶

    My personal library principles allow reusable preferences and deliberate design choices alongside demonstrated fixes. A component can be useful without establishing a defect in the official implementation.

    Require a recurring need or deliberate shared preference, two unrelated applications that actually use the same interface, useful independent tests, documented supported versions, clear licenses and an owner for compatibility/security fixes. Prefer small source components with explicit versions initially. Avoid introducing a new system-wide service or mandatory runtime dependency without a measured need.

    Current direction: preserve tested reuse and record the personal library's principles while maintaining the general guide and focused keyboard contribution. The principles do not create a standalone framework or change an app, launcher or device. Component extraction remains a separate implementation decision.

    Review package and Mesh maintenance¶

    The M5Stack review package separates Template integration from Mesh 0.1.11 maintenance. Both carry bounded-poll and owner-scoped hold cleanup tests, including unrelated-device teardown. It supplies exact source/patch hashes, reproduction steps, licenses and qualified evidence, plus the modular-supervisor rationale. Preparation does not submit a PR or qualify the Template physically. Current personal-library direction is recorded in the agreed principles.
