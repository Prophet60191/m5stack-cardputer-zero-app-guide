    Build your first app¶

    You do not need to read the entire guide before building. Start with a small working screen, then add the facilities your idea actually needs. This route is for CardputerZero running Debian, not the ESP32 Cardputer or Cardputer ADV.

    The short route¶

    1. Define one useful task. Write down what the user can do, what data survives closing, and whether any hardware or network access is required. A local counter needs neither a supervisor nor a setup wizard.
    2. Build the official starting point. Follow the counter walkthrough. It takes you from pinned source to a desktop build and an inspectable arm64 package. No device is needed yet.
    3. Make it yours. Change the greeting, then try the counter reset exercise. Rebuild and check both changes in the simulator. Follow a key press through the viewmodel to the screen before replacing any of the Template's structure.
    4. Choose only relevant extras. Use the table below. Read the linked recipe when adding that capability; the recipe is not a requirement for every app.
    5. Prepare a real app for release. Give it its own identity, handle errors, preserve attribution, and follow build/install checks and security/publishing. A successful build is a starting point, not a release certificate.

    Stop after the greeting if you only want a first working example, or do the reset exercise to add a feature of your own. The fuller reference is there when the next design question arises.

    Which sections do I need next?¶

    Your next need Read next
    Another local screen, a timer, calculator or game Local utilities; UI
    Notes, saved records, drafts or conversations Persistence/messaging; identity and durable intent
    Keyboard text entry Keyboard; evaluate the official input path before adding a decoder
    A website, network service or remote-control connection Networking; security
    GPS, camera, NFC, LoRa or another peripheral Project selector; use the specific peripheral recipe
    Playback or recording Audio/media
    Slow work or more than one resource owner Architecture choices; a separate service is one option
    A Debian installer, upgrade or Store listing Packaging; Store readiness

    Understand the labels¶

    Platform requirements describe the device, launcher and packaging contract. Project recipes apply only to the facilities you use. Personal UI preferences record my chosen appearance and interaction; they are not official requirements. Case studies record what a particular project taught me, with its own test limits.

    Start by inspecting official guidance and code. Reuse what fits; adapt what your app needs. Record the reason for a departure before treating it as a reusable improvement. The component comparison and library principles explain this distinction.

    Keep an honest progress record¶

    Use separate milestones: source builds; desktop behavior checked; arm64 package built and inspected; installed app checked; physical input/peripherals checked; release reviewed. Mark unperformed checks pending, with the reason. A stationary GPS or Wi-Fi check, for example, cannot prove performance while walking a survey.

    The independent-reader check is a short handoff for someone trying this guide without the original chat history. Their experience will tell me which instructions still need work.
