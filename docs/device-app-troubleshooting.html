    The counter demo is installed. What went wrong?¶

    Use this page alongside the first-device app walkthrough. Start with what you see. Check the same .deb you intended to install and change one thing at a time. A good desktop run is useful evidence, but it does not test APPLaunch, the device keyboard, or the libraries on the handheld.

    Why add this page? The official tools describe build and submission requirements. This guide starts from the symptom on the handheld, because a valid package can still have a wrong launcher entry, an unresolved library, or different key behavior. The checks narrow the problem without reimaging the device or changing unrelated packages.

    No app icon in APPLaunch¶

    On the CardputerZero, check the package and the files it owns:

    dpkg-query -W -f='${db:Status-Abbrev} ${Package} ${Version} ${Architecture}\n' cp0-guide-counter-demo
dpkg-query -L cp0-guide-counter-demo | grep '/APPLaunch/'

    Look for ii (installed), the version you intended, and an entry under /usr/share/APPLaunch/applications/ for Guide Counter. Open that package's .desktop file and check [Desktop Entry], Name, Exec, Icon, and Terminal=false. Confirm Exec resolves to this app's executable (not another app's) and Icon resolves relative to /usr/share/APPLaunch/. See the launcher contract. If the entry is wrong, fix the package source rather than editing launcher-owned files or borrowing another package's name.

    The icon is there, but the app closes immediately¶

    Note the time, launch once from APPLaunch, and look only at the matching startup lines. From a terminal in your regular device session, use the launcher’s user unit:

    journalctl --user -u APPLaunch.service --since '2 minutes ago' -n 25 --no-pager

    If that produces nothing, confirm the launcher unit for your image with systemctl --user list-units --type=service. An empty log or an access error does not prove the app ran. Use the first relevant error: a missing path points to package layout; a named missing .so points to a runtime dependency. The launcher can hand off display and keyboard settings that an SSH command does not, so running the binary remotely is not an equivalent launch test.

    For example, an earlier official Camera build expected libcamera.so.0.7, but the device image had libcamera 0.8. The startup error identified a library mismatch, not a broken sensor. Camera v1.0.4 documents its move to libcamera 0.8. That was a Camera fix, not a dependency of this counter. Don't symlink incompatible libraries to silence the message.

    It works on the desktop, but not on the device¶

    On a machine with Debian package tools, inspect the artifact without installing:

    dpkg-deb -f ./your-demo.deb Package Version Architecture Depends
dpkg-deb -c ./your-demo.deb

    Check for arm64, the correct package and files, and dependencies intended for the supported device image. On the device, if file is available, use it on the executable resolved from Exec (not the .desktop file or the .deb). A native device executable should be an ARM aarch64 Linux ELF; if Exec points to a script, check its interpreter and the binary it invokes instead. An arm64 package label does not turn a desktop binary into a device build. See cross-building and packaging.

    Menus open, but the keys do the wrong thing¶

    Start with a short single press and no locked modifiers. From About (the home screen), press 8 to open Counter. In Counter, try C (right) and Z (left), then tap Esc to go back. Test hold Esc separately on About to exit to the launcher; it is not the same as the short back press. If navigation works but the count doesn't change, record the screen and one key that failed before changing mappings. Use the official key map and input checks to compare simulator and hardware; don't turn a mapping issue into a permission fix.

    If asking for help, share the package version and architecture, image version, screen, expected result, and one relevant error line with usernames, device or network identifiers, and personal paths removed. Don't post a raw journal or delete saved data while diagnosing. The steps here are inspection only; they do not require root, a factory reset, or an OS reflash.
